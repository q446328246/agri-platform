@agri/contracts 公共包中，服务再按契约实现。契约是团队之间唯一的接口真相来源。单向依赖：应用依赖公共包，公共包之间不得出现循环引用；服务内部各层只允许上层调用下层，反向通信通过接口或事件实现。约定优于配置：目录结构、文件命名、DTO 校验方式、日志字段统一约定，新成员按约定放置文件即可，减少评审沟通成本。可独立部署：每个服务拥有独立的 Dockerfile、独立环境变量文件、独立健康检查端点，任意服务可单独构建、单独发布、单独扩容。渐进可拆分：初期小规模场景可将多个服务部署在同一进程内聚合运行，规模增长后按服务粒度独立拆分，不因拆分而改动业务代码。1.4　版本口径说明本文档给出的依赖版本采用「主版本号 + 版本基线」的方式表述，不对补丁号作硬性规定。原因是依赖生态更新频繁，锁死补丁号会带来不必要的维护负担；而主版本号决定 API 是否兼容，是必须锁定在文档中的信息。具体执行时遵循三条约定：一是所有依赖的实际版本以 pnpm-lock.yaml 提交入库的锁定版本为准，保证团队与流水线安装结果完全一致；二是升级主版本必须提交技术方案评审，说明破坏性变更与迁移成本；三是每个季度由技术负责人组织一次依赖安全巡检，处理高危漏洞通告。本文档所列版本基线为编制期（2026 年 11 月）的规划口径，用于方案比选与预算编制参考。工程初始化时应当核对各依赖的最新稳定版本，如与本文件存在差异，以工程初始化时的实际稳定版本为准。1.5　文档使用路线建议按以下顺序使用本文档：新建工程时先读第七章，按步骤完成环境搭建与工程初始化；随后按第三章至第五章的目录结构逐个创建服务；进入日常开发后，第六章的依赖清单与第八章的工程规范作为长期查阅手册；需要向他人说明工程构成时，使用第九章的映射表与附录 以模块为装配单元。本工程约定三类模块，职责清晰不混用。功能模块：一个业务能力一个模块，如 PlotModule、GridModule，内部聚合该能力的控制器、服务、仓储实现。基础设施模块：封装技术组件并全局导出，如 PrismaModule、KafkaModule、RedisModule，用 @Global 装饰器避免每个功能模块重复导入。配置模块：通过 registerAsync 方式注入配置，保证配置项在任何服务启动前完成校验，配置缺失直接启动失败而不是运行时报错。模块之间的引用必须在根模块显式声明，禁止跨服务直接引用源码。若两个服务需要共享逻辑，正确做法是把逻辑下沉到 packages 公共包，而不是从一个服务引用另一个服务的文件。工程提供 scripts/check-arch.mjs 校验脚本，在持续集成中自动检查两条红线：一是 apps 之间不得互相引用，二是 packages 之间不得出现循环依赖。违反任一条流水线直接失败。4.4　服务入口与运行模式每个服务的启动入口 main.ts 承担四项固定职责：加载并校验配置、创建应用实例、装配全局管道与过滤器、注册健康检查。入口文件保持简洁，不写业务逻辑。服务支持两种运行模式：一是网关模式，对外暴露 HTTP 接口，需开启接口文档与访问日志；二是微服务模式，仅通过消息队列或 gRPC 提供能力，不监听 HTTP 端口。同一份代码通过环境变量切换模式，便于本地开发时合并部署。第五章　微服务模块划分5.1　划分原则服务划分是这份文档里影响最深远的决策：拆得太粗，一个服务改动牵扯全局；拆得太细，运维与联调成本超过收益。本工程的划分依据四条原则。按业务能力划分，而非按技术层次划分。不设「数据服务」「接口服务」这类技术型服务，而是围绕地块、设备、感知、决策、作业、核算这些业务对象建服务。变更频率一致的对象归入同一服务。地块主数据变更少、遥测数据写入量大但结构稳定，二者天然适合分开；而处方生成与决策规则经常调整，需要独立演进。数据归属唯一。每个业务对象只由一个服务负责写入，其他服务只能通过接口或事件读取，避免多服务同时写同一张表导致数据口径混乱。规模无关的弹性。服务划分与农场规模无关，从百亩级到区县级平台使用同一套服务划分，差异只体现在部署副本数与资源规格上。5.2　服务全景全平台共划分 5-1　微服务划分与服务间通信拓扑5.3　基础支撑域服务5.3.1　gateway 统一网关服务所有外部请求的唯一入口。基于 NestJS 的微服务客户端模块做请求转发，基于 Redis 做分布式限流。网关只做与业务无关的通用处理，不承担任何业务逻辑，避免成为业务演进的瓶颈。路由转发：按路径前缀将请求分发到对应服务，路由规则由配置中心下发，支持灰度分流。身份前置校验：校验令牌有效性与租户标识，把解析出的用户上下文透传给下游服务，下游无需重复解析令牌。限流与降级：基于 Redis 实现令牌桶限流，对高频设备查询接口单独设置阈值；下游服务不可用时返回缓存的只读数据而非直接报错。接口聚合：把一张图所需的「地块信息 + 设备状态 + 当日天气」聚合成单次响应，减少移动端请求次数。文档出口：统一暴露 OpenAPI 文档聚合页，各服务按契约注解生成接口描述，由网关汇总呈现。5.3.2　auth 认证授权服务负责身份与权限，是全平台唯一签发令牌的服务。平台面向农场主、农技员、农机手、监管人员、系统管理员等多类角色，权限模型需要同时支持功能权限与数据权限。认证：账号密码登录、手机验证码登录，密码采用高强度哈希算法加盐存储，登录失败次数限制。令牌：签发访问令牌与刷新令牌，访问令牌短有效期，刷新令牌长有效期并支持主动吊销。功能权限：基于角色的访问控制，角色与权限点绑定，权限点按「服务 + 资源 + 操作」三级命名。数据权限：基于属性规则的访问控制，实现「只能看自己农场的地块」这类行级过滤，规则以地块归属关系为基础。多租户：租户标识贯穿全部请求上下文，租户之间数据完全隔离。5.3.3　plot 地块主数据服务全平台的空间主数据源，是「以地块为最小管理单元」这一设计落地的技术载体。其他服务不存储地块边界与归属关系，全部通过本服务获取。地块建档：记录地块名称、编码、面积、边界坐标、权属、土壤类型本底信息。网格划分：按固定边长把地块切分为管理网格，网格继承地块归属，作为变量作业的最小执行单元。统一编码：按六段式规则生成地块唯一编码，编码一经生成不可修改，作为全平台数据关联的锚点。片区与线路：维护片区层级结构、田间道路线路、水电网管线走向与附属设施位置。作物季管理：记录每个地块每一季的种植品种、播种日期、目标产量，是核算与溯源的关联对象。空间分析：基于 PostGIS 以 SQL 完成地块叠加、缓冲区、相邻关系等运算，应用层不承担几何计算。5.3.4　platform 平台管理服务承载平台自身的运营管理能力，与具体农业业务无关，因此独立成服务以便在多项目交付时整体复用。租户管理：租户开户、套餐配置、资源配额、到期提醒。字典与参数：统一维护业务字典与系统参数，服务启动时拉取并订阅变更。操作日志：记录关键操作的操作人、时间、对象、结果，支持按条件检索与导出。审计追踪：对涉及数据导出、权限变更、配置修改等敏感操作单独留痕，满足等级保护审计要求。任务监控：集中展示各服务的定时任务执行记录与失败重试情况。5.4　感知与控制域服务5.4.1　iot 设备接入服务所有田间设备的接入与管控入口，是数据链路的起点。本服务承担协议适配与设备生命周期管理，不负责业务数据加工。设备接入：设备注册、一机一密认证、连接状态维护，支持 MQTT 长连接与 HTTP 上报两种方式。协议适配：适配 MQTT、HTTP、Modbus、LoRa、NB-IoT 等九类协议，统一转换为内部消息格式后投递到消息总线。离线感知：利用 MQTT 遗嘱消息机制，设备异常断开时由消息代理立即投递离线事件，无需等待心跳超时，实现秒级离线感知。指令下发：接收控制请求并下发到指定设备，带指令回执与超时重试，下发结果写入操作日志。边缘网关管理：管理边缘网关的版本、在线状态、缓存数据补传情况。物模型：定义设备类型、属性、事件、服务，作为数据解析与前端渲染的元数据依据。5.4.2　telemetry 物联感知服务承接设备上行的海量数据，完成解析、落库、告警与查询。这是全平台写入压力最大的服务，因此采用时序数据库承载，并在架构上做写入与查询分离。数据解析：按物模型校验报文完整性，做单位换算与异常值剔除。时序落库：采用批量写入与超时刷盘策略，避免高频小批量写入放大数据库压力。四情归集：把土壤墒情、苗情、虫情、灾情数据按地块与时间维度归集，供一张图与看板查询。阈值告警：按地块、作物、生育期配置差异化阈值，触发后生成告警事件并通知消息服务。聚合统计：按小时、日、周、生育期做均值、极值、累计值预聚合，看板查询直接读取聚合结果。数据补传：处理边缘网关断网期间缓存数据的补传，按时间戳去重写入。5.4.3　weather 气象服务对接外部气象数据源并做本地化加工，为首页天气面板与作业适宜性判断提供数据支撑。该服务对外部数据源强依赖，因此独立部署，便于数据源切换与故障隔离。数据源对接：接入公共气象数据接口与田间气象站实测数据，两者互相校验。五日预报：提供当前地区未来五天天气状况，供首页固定面板展示。作业适宜性：结合降水量、风速、温度判断当日是否适宜喷药、施肥、播种等作业，输出适宜、谨慎、不宜三档结论。缓存策略：预报数据按地区缓存并设定有效期，避免重复调用外部接口造成配额浪费。5.4.4　control 装备控制服务把作业计划翻译为设备可执行的指令序列，并对执行过程做安全约束。服务与 iot 的边界是：control 决定「做什么、做多少」，iot 负责「把指令送到设备」。播种控制：创建自动播种任务，设定播种密度与行进速度，按网格变量调整下种量。灌溉控制：支持按区域差异化灌溉与定时灌溉，按墒情数据触发补灌，避免大水漫灌。水肥一体：设定肥料混合比例，控制搅拌时长与输送流量，按电导率与酸碱度实时校准浓度。除草控制：下发除草装备作业参数，支持按作业幅宽与行走路径配置。联动策略：预置墒情与灌溉、气象与喷药、肥液浓度与搅拌时长等联动规则，触发条件满足时自动执行。安全约束：任何控制指令下发前校验设备在线状态、管道压力上限、累计灌溉量上限，超出安全范围直接拦截并告警。5.4.5　video 视频监控服务管理视频流与录像资源，并叠加视频智能分析能力，让视频从「事后查看」变为「实时发现」。流媒体接入：对接流媒体服务器，按需拉流，避免全部通道常驻拉流造成带宽浪费。云台控制：支持转动、变焦、预置位设置与巡航。录像回放：按时间轴检索与回放，支持事件片段标记与快速定位。智能分析：对长势识别、越界入侵、灾情识别等场景做视频分析，分析结果投递到感知服务与苗情档案。互相印证：视频发现与传感器告警在时间轴上对齐展示，便于判断告警真实性。5.5　业务与决策域服务5.5.1　decision 智能决策服务全平台的智能中枢，采用「规则引擎 + 模型服务」的混合架构：可明确表述的经验知识用规则实现，保证透明可维护、农技人员可自行调整；影像识别与趋势预测交给模型服务，各司其职。规则求值：加载地块、作物、生育期、墒情、气象等条件，输出施肥、灌溉、植保建议。规则热更新：规则以数据形式存储，修改后即时生效，无需重启服务。模型调用：通过桥接适配器调用 Python 算法服务，完成病虫害识别、产量预测、遥感反演等任务。处方生成：把规则结论与模型结论合并为地块级处方，明确作业类型、用量、时机、执行网格。决策留痕：记录每次处方生成所依据的输入数据与命中规则，便于事后复核与责任界定。效果回流：处方执行结果与最终产量回写规则库，作为参数调优依据。5.5.2　operation 作业调度服务把处方转化为可执行的作业任务，并调度农机与无人机完成作业，是全平台「决策到执行」的闭环环节。任务派发：按地块、作业类型、时间窗生成作业任务，支持指派到具体农机手或接入社会化服务队伍。路径规划：为农机规划田间作业路径，考虑地块形状、转弯半径、机具幅宽，减少空驶与重压。无人机植保联动：接收虫情事件后自动生成植保任务，规划航线并派遣无人机前往虫情位置喷洒对应药剂，形成「发现—审批—派单—作业—回传」五步闭环。避让与安全：多机作业时做航线避让；作业前校验气象条件是否适宜，风速或降水超限时自动挂起任务。作业留痕：记录作业轨迹、作业面积、实际用量、作业影像，作为补贴申报与溯源凭证。进度看板：按地块展示作业进度，未按期完成的任务自动提醒。5.5.3　finance 经营核算服务以地块为核算单元，把分散在多个服务中的数据归集为可读的成本收益结果。这是「一块地一核算」设计原则的技术落点。投入归集：汇总种子、化肥、农药、水费、电费、农机作业费、人工费等投入项，按地块与作物季归集。产量记录：记录各地块的实际产量与品质等级，支持地磅数据对接与人工录入两种方式。收益核算：按地块计算单位面积成本、单位面积产值、纯收益，自动识别低产低效地块。对比分析：支持同作物多地块横向对比、同一地块跨年度纵向对比。报表输出：生成经营报表与补贴申报辅助材料，数据可导出为表格文件。5.5.4　trace 质量溯源服务把生产过程中的关键记录串联为可对外展示的溯源档案，服务于品牌溢价与质量监管。档案归集：从地块、农事、作业、投入、检测等环节抽取关键节点，生成生产档案。溯源码生成：按批次或地块生成唯一溯源码，支持一物一码与一地块一码两种模式。扫码查询：面向消费者的公开查询页面，展示产地环境、作业记录、投入品使用、检测报告。防伪校验：记录扫码次数与地域分布，异常高频扫码时提示风险。5.6　公共支撑服务与公共包5.6.1　message
